# Матрица требований и покрытия

Основание: задание 1, вариант A, страницы 2 и 5-16 исходного PDF. Номера в этой матрице совпадают с печатной нумерацией исходного PDF. Страницы 3-4 описывают другие профили заказчика и не выбираются для задания 1. Профиль A - кадровое агентство; сквозной сценарий - «новая вакансия → проверяемый short-list → утверждение рекрутером».

Матрица показывает, где описано решение и чем его следует проверять. Слова «предусмотрено» и «проверить» не означают успешного испытания. Фактические результаты находятся в [measurements.md](measurements.md) и файлах evidence. До появления соответствующего протокола условие остаётся неподтверждённым. Учебный пилот и целевая промышленная архитектура различаются явно.

Число 20 описывает активные задания, а не 20 одновременных генераций. API и оркестратор работают в одном процессе, тяжёлое сравнение и модели запускает compute.py через ProcessPoolExecutor spawn. На RX 6900 XT выбран один GPU-процесс с Qwen3-4B FP16 и MiniLM FP16. Другие задачи могут ожидать или проходить немодельные этапы. ROCm/PyTorch и eager attention фиксируются в протоколе. Поддержка vLLM этой картой не заявляется. Приложение валидирует JSON подсказок, а их смысл проверяет рекрутер по источникам.

Фактический GPU-протокол: два запуска Qwen3-4B FP16, 230 входных и 111 выходных токенов, 9,761 / 10,363 с, оба JSON ready, рейтинг и цитаты неизменны. Загрузка заняла 7,902 с; peak allocated 7,63 GiB, reserved 7,67 GiB. Эти короткие запросы не проверяют максимум контекста или исчерпание VRAM. Приблизительные 0,10 генерации/с дают 1,4 GPU-часа на 500 вызовов или 14 часов на 5 000. Для расчёта принят вариант 10% операций с LLM; 100% потребуют около двух GPU на восьмичасовой день без гарантии пика. Запас на очередь и смешанную нагрузку оценивается отдельно.

## Реализованный PDF-вход и интерфейс

POST /api/resumes/pdf принимает multipart с одним PDF и полями кандидата. GET /api/resumes/{id}/pdf возвращает оригинал только рекрутеру разрешённого проекта. GET /api/tasks/{task_id}/sources/{resume_id} открывает неизменяемый снимок текста, использованного задачей: последующее обновление текущей записи не меняет основание старой цитаты. Операции оставляют аудит метаданных без текста или Base64.

documents.py использует pypdf 5.6.0 в отдельном Python -I subprocess с чистым окружением. Пределы: два одновременных разбора без ожидания, восемь секунд wall time, CPU soft/hard 6/7 с, 512 MiB памяти, 20 страниц, 5 MiB файла, 6 MiB multipart-тела и 30 тысяч символов. Перегрузка возвращает 429 с Retry-After: 1, размер 413, неподдерживаемый либо повреждённый PDF 422 с понятной причиной. Сканам нужен OCR, которого в пилоте нет. Процесс с лимитами не считается полной OS-песочницей.

Оригинал находится в SQLite отдельным kind=attachment в Base64; бинарное содержимое не копируется в resume/task и входит в SQLite backup. Набор data/resumes содержит 32 синтетических PDF из неизменённых fixtures и manifest. experiment_pdf.json подтверждает успешное извлечение 32/32 файлов, совпадение профессиональных признаков трёх контрольных short-list и точные цитаты. Этот опыт относится к baseline и не заменяет отдельную GPU-проверку PDF-сценария.

Интерфейс предлагает фильтры очереди «Все», «На проверке», «Утверждены», карточки кандидатов и вложенную карточку исходного резюме с возвратом к прежней прокрутке и фокусу. Выбор кандидатов и контекст сохраняются при опросе статуса. В браузере доступен CSV, форматы JSON и Markdown сохранены в API. Утверждение короткого списка остаётся явным действием рекрутера.

По с.12 полный промышленный прототип не обязателен. Требуется минимум один воспроизводимый технический эксперимент с результатами в обосновании архитектуры. Пилот предусматривает baseline, локальные embeddings, GPU-генерацию и проверки устойчивости; фактическое наличие результатов сверяется с приложениями.

Полный набор pytest: 96 проверок, все прошли за 18,17 с, ошибок 0. PDF GPU-прогон прошёл до waiting за 20,611 с с холодным вычислителем после рестарта: 11 доступных PDF-резюме, восемь карточек с вопросами, две подсказки, обе модели device=cuda. Разбор файлов выполнен seed до таймера; 20,611 с не измеряют upload и parse. Исторический прогретый текстовый запуск 9,486 с сохранён отдельно. Human approval остаётся обязательным. runtimeModelOOM не проверен: обычный пик VRAM не заменяет исчерпание памяти. Корректный JSON не доказывает фактическое содержание подсказки.

| Эксплуатационные | 13 | Восстановление по регламенту и измеренное время |
| Регрессионные | 13 | Повтор тестов до допуска нового релиза/модели/парсера |

| Критерий оценки с.14 | Баллы | Покрытие |
|---|---:|---|
| Заказчик и бизнес-процесс | 12 | Паспорт, §1-3 |
| Целостность архитектуры | 16 | §5-7, диаграммы |
| Инференс и ресурсы | 14 | §11-13 |
| Жизненный цикл и оркестрация | 10 | §7-8 |
| Безопасность и изоляция | 15 | §9, 14 |
| Интеграции и инструменты | 8 | §10 |
| Наблюдаемость, эксплуатация, восстановление | 8 | §15-17 |
| Масштабирование и экономика | 7 | §18 |
| Испытания и измеримость | 7 | §19-20, measurements.md |
| Материалы и защита | 3 | Единая терминология, диаграммы, ≤12 слайдов |

Итого 100 баллов: 90-100 - отлично, 75-89 - хорошо, 60-74 - удовлетворительно, ниже 60 - существенная переработка. По с.15 баллы снижают абстрактный проект без процесса заказчика, чат вместо системы, список технологий вместо потоков/ответственности, неограниченные права, опасное выполнение без изоляции, отсутствие расчётов, смешение активных задач с LLM-конкурентностью, обновление без регрессии и декларативное масштабирование.

Обязательные условия допуска со с.14: штатная работа без публичного AI; локальный/полностью контролируемый модельный контур; роли, ограничения и изоляция опасных операций; аудит и остановка; хотя бы приблизительный расчёт ресурсов/конкурентности; минимум один путь восстановления; измеримая программа испытаний; один конкретный выбранный профиль. Оставшееся неподтверждённое условие не скрывается успешным запуском другой части системы.
